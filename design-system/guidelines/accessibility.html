Accessibility is a system constraint

Accessibility is not a final audit layer. It defines how every component and pattern behaves for keyboard users, screen-reader users, low-vision users, motion-sensitive users and people working under cognitive load.

Accessibility principles

Perceivable

Text, contrast, state cues, charts and feedback must be understandable without relying on color alone.

Operable

Every interactive path works with keyboard, visible focus and adequate target size.

Understandable

Labels, hints, errors and guidance should explain what happened and what to do next.

Robust

Use semantic HTML first. ARIA enhances meaning only when native elements cannot express it.

Required accessibility checklist

Keyboard path

All tasks can be completed with keyboard only; tab order follows task order.

Focus management

Focus moves into overlays, returns to opener and never disappears behind hidden content.

Names and roles

Interactive elements have accessible names; custom controls expose correct role and state.

Target size

44px minimum target; 48px preferred for touch-heavy candidate and session controls.

Contrast

4.5:1 for body text, 3:1 for large text, icons, focus rings and UI boundaries.

State clarity

Status is communicated with label plus visual cue; no color-only states.

Motion

Reduced-motion equivalent exists for every animation or transition pattern.

Recovery

Errors explain how to fix the issue and preserve entered work whenever possible.

Usage rules

Use native elements first

Prefer button, anchor, input, select, textarea, table and dialog semantics before adding ARIA. ARIA does not repair a non-semantic control.

Do not hide meaning in visuals

Icons, colors, chart marks and progress indicators need labels, legends or text equivalents when they communicate status or instruction.

Session accessibility is stricter

Session controls must remain stable, reachable, labeled and recoverable because the user is under cognitive load.

Verify states, not just screens

Check empty, loading, error, disabled, selected, focus, reduced-motion and long-content states before reusing a component or pattern.

Implementation rule: every reusable component and pattern needs keyboard behavior, focus treatment, accessible name, target size, contrast, non-color state cue, reduced-motion behavior and recovery guidance defined before adoption.
