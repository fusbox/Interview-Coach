Components are product objects with contracts

A component is not a styled box. It owns a job, anatomy, variants, states, token dependencies and usage rules. Future implementation work should select the component role first, then apply foundations through the contract below.

Component taxonomy

Actions

Buttons, icon buttons, avatar-style launchers, split actions and session controls.

Inputs

Fields, textareas, selects, comboboxes, checkboxes, switches, radios and steppers.

Navigation

Tabs, segmented controls, rails, breadcrumbs, mobile docks and route steppers.

Feedback

Alerts, toasts, validation, status pills, progress, loading and saved/queued states.

Data display

Tables, list rows, metrics, score cards, chart shells, trend previews and QA summaries.

Surfaces

Cards, widgets, panels, sheets, dialogs, popovers and candidate action surfaces.

Session objects

Prompt cards, transcript turns, recording states, timers, turn-taking and control bars.

Content objects

Empty states, educational callouts, guidance blocks, debrief sections and reflection prompts.

Required state checklist

Interactive

Default, hover, focus-visible, active/pressed, selected/current, disabled and loading.

Feedback

Success, warning, neutral, queued, saved, needs review and in-progress states with text labels.

Content

Empty, loading, partial data, long text, missing optional media and narrow viewport behavior.

Motion

Reduced-motion equivalent is defined before any animation is accepted.

Accessibility

Keyboard path, aria label/name, visible focus, contrast and minimum target size.

Density

Compact for admin/QA, comfort for dashboard/setup/debrief, focus for core session.

Composition

Component anatomy is explicit. Avoid anonymous nested boxes and equal-radius card stacks.

Token use

Color, type, spacing, shape, elevation, icon and motion roles are named in the component spec.

Usage rules

Use component roles before visual taste

Choose Button, Widget, Row, Panel, Overlay or SessionObject based on the job. Then apply semantic tokens. Do not create color-named variants like blue card or orange button.

Audit current implementation after roles are named

Do not preserve existing app classes because they exist. First decide the desired component role; then rename, consolidate or remove current UI objects that do not match.

Separate components from patterns

A component is a reusable object. A pattern is a composed workflow such as invite creation, candidate setup, coach-planned practice, debrief or session flow.

Protect product-specific exceptions

Avatar-style launchers, candidate action widgets and session controls can have special treatment only when their product job is named and repeatable.

Implementation rule: every component spec should include job, anatomy, variants, states, token dependencies, accessibility, responsive behavior, and non-use guidance before it is promoted into the product UI.
