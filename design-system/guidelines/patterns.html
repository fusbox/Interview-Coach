Patterns compose components into product workflows

A pattern describes the repeatable structure of a task: what the user is trying to do, what the system must reveal, which components assemble the experience, and how the flow behaves across route, density, state and viewport.

Pattern taxonomy

Public funnel

One public landing experience with audience routing for current/potential candidates and clients.

Form flow

Multi-step creation and setup flows with progress, save state, validation and recovery.

Dashboard workbench

Protected overview pages that combine navigation, metrics, next actions and lists.

Candidate learning hub

Preparedness, coach update, planned questions, skill/category views and practice guidance.

Session shell

Shared candidate practice experience with prompt, transcript, controls, state and focus guardrails.

Debrief flow

Post-session feedback, reflection, feedforward indicators and next best action.

Admin/QA operations

Recruiter dashboard, QA review, tables, filters, assignments and exception handling.

Cross-cutting UX

Consistent action placement, statuses, empty states, loading, errors and responsive behavior.

Required pattern checklist

User goal

State the user intent, success condition and the moment the pattern serves.

Route frame

Name the frame archetype: public, protected, form flow, dashboard, session, debrief or ops.

Composition

List the components used and their roles. No anonymous layout piles.

State model

Define empty, loading, partial, complete, error, warning, saved, queued and disabled behavior.

Primary action

Place the next action consistently and define secondary/back/cancel behavior.

Density

Use compact, comfort or focus density based on workflow, not page owner preference.

Responsive order

Define mobile reading and action order before expanding to desktop.

Access and recovery

Keyboard path, focus management, recovery copy, privacy boundaries and reduced motion.

Usage rules

Patterns are workflows, not pages by filename

Use the same pattern for the same user task across recruiter and candidate apps, even when route names or data sources differ.

Start from desired behavior

Do not inventory the current app first. Define what the pattern should do, then audit existing UI against that target.

Keep product exceptions named

If a candidate dashboard action widget, session surface or public marketing treatment diverges, name the pattern and repeatable reason.

Coach voice gets a named surface

Use the coach-voice surface when the product interprets, recommends, or explains: surface-base, a 2px primary edge, calm compass avatar, and restrained raised-1 elevation. Place it on an alternate parent surface when layering is needed; do not reuse it for neutral labels or ordinary form instructions.

Cross-cutting consistency wins

Equivalent interactions should use equivalent components, placement, state labels and recovery behavior across the app.

Implementation rule: every pattern spec should include goal, route frame, component composition, state model, primary action, responsive order, accessibility, recovery behavior and non-use guidance before agents implement or refactor a workflow.
