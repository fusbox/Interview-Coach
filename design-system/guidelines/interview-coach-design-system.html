01

Foundations

The perceptual primitives every component and pattern is built from. Nothing here renders a UI on its own — these are the raw materials (color, type, space, motion…) and the rules that govern them.

1.1

Principles

The few tenets that resolve judgment calls when specifics don't.

Pending

Will hold: the 3–5 design tenets — draft candidates from the product voice are calm & encouraging, positive-only (never a red mark), and never patronizing. Confirm and promote.

1.2

Brand

Blue leads as the single action color; viridian and warm orange are the two accents; TA is the release logo.

Blue (#0B57CE) is the only action color and carries a full interaction set (hover · active · deep · soft). Viridian (#17A079) and warm orange (#E8742E) are accents — base + a soft tint each — used sparingly, never as competing calls-to-action. All variants follow the derivation recipe below.

Logo rule: release surfaces use the TalentArbor / TA mark. Rangam can remain in parent/provenance copy, but it is not a default in-app logo placement.

1.3

Color

The neutral foundation, preparedness ramp and semantic states, plus storage/display conventions.

Neutrals. Candidate surfaces use the RGB neutral set: deep slate ink, restrained secondary text, placeholder-only gray, hairline borders, and airy blue-white surfaces.

Preparedness ramp. Ordered, positive-only growth scale.

Semantics. Success #298646 and Warning #E2B926 are nudged away from Viridian and warm orange; Critical stays #EF4444 and Info tracks primary #0B57CE. Success and warning ship soft/text companions for chips and tinted panels. Tinted surfaces still carry the extracted-app values and are pending review.

1.4

Typography

Manrope display with Inter body/UI, expressed as semantic type-role tokens.

Typography is applied by role. Components should prefer classes/tokens such as .type-display-xl, .type-body-md, .type-eyebrow, and .type-metric-value over raw size/weight choices. The role token includes family, size, weight, line height and letter spacing where relevant.

Line-height and tracking rule: Manrope display stays tight but not squeezed (0.98–1.12, zero tracking); Inter body carries the reading load (1.55–1.8); labels use compact line-height; eyebrows and micro labels are the only styles with intentional positive tracking.

1.5

Iconography

Functional lucide-style glyphs use semantic icon roles aligned to typography density.

Iconography is not logo usage. Logos live under Brand; this section governs functional glyphs: navigation, controls, status, launchers, empty states and icon capsules.

System rule: use lucide-style outline icons only. Keep the 24x24 viewBox, currentColor stroke, round caps/joins, and role-based sizes. Icons can stand alone only for universally understood controls with accessible labels; status and learning concepts should pair icon plus text.

Pending

Will hold: the lucide stroke set (24×24, stroke 2, round caps), the icon-in-capsule pattern, and consumer delivery notes.

1.6

Spacing

A 4px rhythm translated into semantic gaps, padding and workflow density.

Spacing is applied by intent. Components should prefer role tokens such as --gap-field, --gap-cluster, --pad-card, and --density-focus-pad over one-off margins and padding.

Operational rule: primitives define the allowed values; semantic roles define meaning. Compact recruiter/admin surfaces, comfortable candidate learning surfaces and focused session surfaces use the same scale with different defaults.

1.7

Layout & grid

Route frames, grid primitives and wireframing passes before component composition.

Layout is page intent made spatial. Before styling a view, choose the frame archetype: public, protected workspace, form flow, dashboard, session, debrief or ops console.

Wireframe rule: mobile order comes first, then desktop expansion. A rail, drawer, sticky header or launcher is earned only when it protects the primary task.

1.8

Shape

Object silhouettes: controls, rows, cards, widgets, panels, session shells, overlays and pills.

Shape is applied by role. Components should use semantic shape tokens such as --radius-control, --radius-widget, --radius-session, and --radius-pill instead of picking a local rounded class by taste.

Nested radius rule: an inner surface should be visibly tighter than its parent. Avoid equal-radius card-inside-card stacks unless the inner object is intentionally floating or interactive.

1.9

Elevation

Depth, borders and state changes that make hierarchy legible without card sprawl.

Elevation is applied by role. Components should use semantic roles such as --elevation-row, --elevation-card, --elevation-widget, --elevation-overlay, and --elevation-cta.

Depth rule: use borders for structure, shadows for hierarchy, floating depth for overlays, and glow only for primary actions or selected launchers. Selected states should prefer ring/border over larger shadows.

1.10

Motion

Durations, easing, state choreography and reduced-motion behavior across controls, surfaces, overlays and sessions.

Motion is applied by intent. Components should use semantic roles such as --motion-control-duration, --motion-surface-duration, --motion-overlay-duration, and --motion-page-duration instead of local transition timing.

Motion rule: motion must explain feedback, hierarchy, continuity or focus. Candidate dashboard widgets may carry subtle polish; recruiter/admin and session surfaces should remain restrained and predictable.

02

Components

Reusable product objects with named jobs, anatomy, variants, states, token dependencies and usage rules. Components consume foundations; patterns compose components into workflows.

Components are contracts, not a gallery. Each component must define its job, anatomy, variants, required states, responsive behavior, accessibility requirements and token dependencies before implementation work treats it as reusable.

Component rule: choose the component role first, then style it with semantic foundations. Do not preserve existing app classes by default; audit current UI after the desired component roles are named.

03

Patterns

Reusable workflow compositions that assemble components into product experiences: route frames, task flows, dashboard structures, session shells, debriefs, admin operations and cross-cutting UX behavior.

Patterns are workflows, not decorated pages. Each pattern must define the user goal, route frame, component composition, state model, primary action, responsive order, accessibility and recovery behavior.

Pattern rule: define what the workflow should be before auditing the current app. Equivalent interactions should use equivalent components, state labels, placement and recovery behavior across recruiter and candidate experiences.

04

Voice & content

Product language rules for the calm, encouraging coach voice: tone, microcopy, casing, emoji restraint and shared domain vocabulary across recruiter and candidate experiences.

Voice is part of the interface. Content should make the next action clear, reduce pressure and preserve the candidate's sense of agency without becoming vague or overly cheerful.

Content rule: use plain, specific coaching language. Prefer feedforward and next best action over judgment; keep labels consistent for practice rounds, question sets, preparedness states and debrief guidance.

05

Accessibility

Shared accessibility foundation for both audiences: focus visibility, target size, contrast, non-color cues, keyboard behavior and reduced-motion expectations.

Accessibility is a system constraint. Components and patterns must preserve focus visibility, adequate target size, semantic state labels, contrast and reduced-motion alternatives.

Accessibility rule: every interactive component needs keyboard reachability, visible focus, an accessible name, non-color state cues and a reduced-motion equivalent before it is considered reusable.
