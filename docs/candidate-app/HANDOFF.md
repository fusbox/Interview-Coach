## Current State

- The rebuild is intentionally cleanroom. Bring old app code back only when a numbered slice needs it, and favor V2 contracts over V1 code unless V1 is clearly more fit for the job.
- Public root, `/candidate/launch`, dev launch, `/candidate/setup`, `/candidate/practice/ready`, `/candidate/practice/ready/[intentId]`, `/candidate/session/[sessionId]`, and `/candidate/dashboard` exist.
- Host launch has dev-mode token minting, production token verification scaffolding, candidate launch-session storage, and fail-closed orchestration. Production TA/RW launch-context lookup is still the major missing adapter.
- `/candidate/setup` is the generic new-prep-context setup surface. It preserves unsubmitted local browser drafts and validates the typed setup contract before submit. An explicitly supplied profile is ownership-checked. Manual setup creates path one when no exact candidate + normalized role/JD match exists, repair-reuses only a matching profile with no sessions, and returns a candidate-owned choice dialog instead of silently reusing any matching profile with activity. The dialog can canonicalize to the selected dashboard context or explicitly create a new independent `role_profile_id`; closing or a failed separate-path write preserves the draft. Production launch identity without a trusted host-resolved profile fails closed. The created session stores non-null `role_profile_id`, and the UI clears the setup draft only after session creation or an explicit existing-path choice. The provisional browser bridge remains a nonproduction-only exception when durable identity/storage is unavailable. Follow-up practice setup must not be rendered through this generic setup surface.
- `candidate_practice_sessions` is the main V2 durable session boundary. It stores candidate ownership, setup snapshots, question-plan snapshots, optional wording state, progress state, answer drafts, pending answer submissions, accepted analysis snapshots, feedback action events, candidate-led completion snapshots, and follow-up attempt lineage. `planned` means no answer has been accepted; the first accepted answer promotes the session to `in_progress`, where it remains until explicit completion. Completed or abandoned sessions reject new accepted-answer writes. Migration 012 repairs historical answered rows that were left `planned`. In explicit local dev host-launch mode, routes resolve deterministic `dev-host-launch-*` cookies to fixture candidate profiles without treating those cookie values as DB launch-session ids.
- The candidate session now enters a shared one-question live-practice shell driven by neutral session runtime facts. It provides role/question progress, candidate-ready typed-answer capture, debounced and serialized durable draft saves, exact-question and draft recovery, distinct submit-versus-analysis recovery, candidate-safe coaching, and a persistent candidate exit to `/candidate/dashboard` that does not reset progress. Candidate and invited adapters share the shell while retaining distinct mutation, completion, and return behavior. Legacy `question_preview` progress is migrated to the equivalent live question; preview navigation and Back to plan are no longer candidate product UI.
- Initial and follow-up candidate-led rounds render through one production-shaped pre-session landing composition. Initial rounds transition from the durable session record. Every new follow-up round assembled from an existing prep context, whether one question or many, must route through `/candidate/practice/ready/[intentId]`; direct intent creation may bypass the editable builder but not the landing. Only an already-started or consumed round may resume directly. Both entry types use candidate-led preparation/no-hiring-decision copy, pause-and-return reassurance, one primary action, and the 1.25-second "Entering practice space" overlay. The overlay fades in over the landing, holds while the live shell mounts underneath, then fades away; reduced-motion users receive the same orienting state without animation. A shared invited-practice module provides the future initials-confirmation -> invited landing variant with recruiter-visibility and original-invitation-return copy, but no invite route or persistence mutation is wired yet.
- The shared question-audio lifecycle defines landing Q1 prefetch, current/next prefetch, user-gesture unlock, and browser-session play-once memory. No production TTS transport is wired: V1's TTS route is coupled to legacy authorization and must not be copied. Production question wording, answer-analysis and Coach Update providers, media capture, and invited route convergence remain pending.
- `/candidate/practice/ready` is the follow-up practice bridge. Query-pointer actions are validated against candidate-owned facts, durable `candidate_practice_intents` support one or many selected questions, `/candidate/practice/ready/[intentId]` renders staging, and `/candidate/practice/ready/[intentId]/start` creates follow-up `candidate_practice_sessions` with source intent, source question, session attempt, and question attempt lineage. Repeated practice is intentionally unlimited.
- `/candidate/dashboard` consumes typed V2 read models derived from candidate-owned `candidate_practice_sessions` plus completed versioned Coach Update artifacts. It chooses a selected candidate-owned prep context before making dashboard claims, shows active-round resume state, Coach Update, Plan Progress, Practice from Feedback, latest-round review, focused-practice actions, and follow-up attempt rollups. Headline and per-context answered/coached evidence includes active and completed rounds, counting each submitted question occurrence once and counting coaching only when the latest submission has matching accepted analysis. Retry attempts remain separate lineage and do not inflate those question widgets. The latest Coach Update appears only when a completed artifact matches the exact latest selected-context round; unanswered items remain outside its detail. Canonical navigation is `/candidate/dashboard?prep=<roleProfileId>`; profile selection is ownership-scoped, same-title profiles remain separate, and session exit/completion plus follow-up staging return to the session or intent's profile. Bare, malformed, stale, or unauthorized profile selectors choose the normal candidate-owned fallback once and canonicalize. `targetRole` remains a bounded compatibility selector only for historical records whose `role_profile_id` is null and cannot select profile-backed work. Plan Progress creates one durable multi-question intent for unanswered planned coverage, and Practice from Feedback resolves the coached-question intent; neither follow-up path uses generic setup. Attempt lineage is data infrastructure for later trend, recruiter, and BI uses; the current read-model attempt rollup is scaffold metadata rather than the normalized source for future candidate, recruiter, or BI attempt totals, and attempt UI is not a current requirement.
- QA/evaluation has a typed V2 export contract for answer-quality review and model A/B comparison. It derives redacted fixed cases, model/prompt/evaluator run snapshots, and same-input comparison snapshots. It intentionally does not include a candidate-app versus recruiter-app source axis because V2 AI calls should be evaluated as one interview-coach evaluator job.
- Normalized `candidate_answer_attempts` and `candidate_answer_evaluation_runs` preserve immutable answer and evaluator lineage independently of the slot-keyed latest-result JSON. The answer-submit route appends or replays attempt one, authorizes feedback retry only from the exact latest analyzed attempt and saved retry action, appends the retry under a slot lock, and projects stable attempt identity into `answer_submissions_json`. The evaluator-run repository supports candidate-owned start, replay-safe completion/failure, provider/model/prompt/evaluator metadata, and multiple same-input runs. The local fixture analysis route now claims and completes one accepted `candidate_coaching` run before updating the compatibility projection; production provider wiring must implement and fault-test the same contract.
- The ratified [evidence-first evaluator contract](./05-quality/evidence-first-evaluator-contract.md) fixes one immutable answer attempt as the evaluation unit; validates exact answer spans and category signals; separates applicability from observed qualitative bands; requires versioned references for technical correctness; conditionally verifies risky claims; validates candidate coaching against accepted evidence; and defines provider metadata, timeout/retry, redaction, telemetry, QA, and candidate-safe projection policy. The local fixture now exercises the same typed extraction, deterministic appraisal, feedback-validation, and candidate-safe projection boundary without pretending to be the production model pipeline.
- Candidate feedback now renders one stage at a time from candidate-safe evidence-first facts: acknowledgement, focused content coaching, optional delivery coaching, then next step. Every selected transition is persisted before it executes and is recovered only for the exact analyzed attempt. Continue/finish and skip retain candidate control. Retry is offered only when immutable attempt identity exists; choosing it reopens the preserved answer and a successful submit appends a linked attempt rather than overwriting history. Provider/analysis retry remains a new evaluator run on the same answer attempt.
- The ratified [evidence-first dashboard information architecture](./04-architecture/evidence-first-dashboard-information-architecture.md) makes opaque candidate-owned prep-context identity authoritative; distinguishes immediate in-session feedback from a versioned post-session Coach Update synthesis; limits Coach Update detail to practiced questions; keeps unanswered plan coverage in Coach Plan/Practice Next; and separates a durable editable next-round draft from immutable launch intents. Title-keyed scoping is now isolated to historical null-profile records; duplicate review surfaces and dashboard-local queue language remain compatibility scaffolds, not the final contract.
- Durable `candidate_next_round_drafts` now provide one candidate-owned editable queue per opaque prep context, with normalized ordered source-question items, provenance, a 20-item capacity, and optimistic versioning. Add/remove/clear/reorder operations lock and mutate only the exact owned version. `public.snapshot_candidate_next_round_draft_to_intent(...)` revalidates evidence and exact item assembly, creates one immutable `practice_builder` intent, clears the draft items, and advances its version atomically. Duplicate launch recovers the same ready intent or consumed session. Queue-created session snapshots retain draft/version/item/provenance lineage, and follow-up question lineage resolves a canonical root across repeated follow-ups so attempt numbering does not fork or reset. Direct one-question and fixed-bundle intent paths remain unchanged. This is infrastructure only: no final queue UI is wired.
- Current persistence posture: dashboard meaning remains a read-time derivation until multi-round aggregation, query pressure, or analytics needs justify projections. Exact post-session Coach Update wording is the bounded exception: it is now a versioned source-linked operational artifact for stable replay and QA, not persisted preparedness truth.

## Open Decisions And Risks

- Production `/candidate/launch` remains fail-closed until the TA/RW launch-context lookup adapter is implemented and configured.
- Host-launch replay protection, secret rotation, token lifetime policy, issuer/audience guarantees, and exact production cookie/session behavior are not fully specified.
- Identity-backed setup draft persistence remains pending; local browser setup preservation does not satisfy the production new-device requirement.
- Resume ingestion still needs product and technical decisions for upload, OCR/photo capture, PDF extraction, PII handling, storage, and when extracted text becomes the setup payload. Later resume revision under the same prep context must stage a versioned resume label/snapshot, preserve historical session inputs, and reconcile existing plan questions through candidate-approved slot-preserving replacements rather than silently rewriting them.
- Production question-wording and answer-analysis providers need prompts, credentials, retry/error handling, observability, redaction, and QA capture policy.
- The evaluator contract is ratified but not wired to a production provider. Technical-reference ownership, raw-output retention exceptions, and durable evaluator-run claim/retry/concurrency semantics remain decisions before replacing fixture analysis. Production provider work must satisfy the [development fault-injection and browser/DB failure matrix](./05-quality/evidence-first-evaluator-contract.md#production-provider-failure-validation-gate); the current deterministic fixture cannot prove that integration behavior manually.
- Slot-keyed answer/analysis JSON remains a latest-result compatibility boundary. Fixture analysis now records each accepted coaching invocation as an evaluator run against a fixed answer attempt before updating that projection; production provider wiring must preserve the same claim, validation, and terminal lifecycle rather than bypassing it.
- The shared audio lifecycle has no production TTS adapter or authorization contract. Preserve the prefetch/play-once boundary while replacing V1's legacy candidate-token route with a V2 identity-owned transport.
- The final feedback stage executes the fixed candidate completion mutation and selected-context dashboard return. Its final visual and transition treatment remains open for product refinement.
- Follow-up practice intent creation plus session creation works, but production transaction hardening around intent consume/session create remains pending.
- Queue launch requires one opaque prep context and one coherent staged setup snapshot. The product does not intentionally assemble a round across role profiles, stages, or resume postures. The current matching guard is therefore an integrity boundary, not an unresolved mixed-context product option. Future resume revisions must define which version is staged on the ready landing before queued questions are launched.
- Historical sessions and intents whose `role_profile_id` is null remain readable through isolated title-keyed compatibility behavior. New profile-backed work must never be grouped or selected by role title. Migration 010 backfills intent identity only when it can be traced to a candidate-owned source session; malformed legacy multi-context intents remain fail-closed at follow-up session creation.
- Manual prep-context resolution detects candidate + normalized role + normalized JD hash matches but no longer silently reuses profiles with activity. `practice_path_number` permits explicit independent duplicate UUIDs without becoming user-facing identity or inherited lineage. Production same-title/same-JD job separation still requires the confirmed JobCollectionID/RequirementID schema and host adapter; do not extend the manual key as a substitute for trusted platform identity.
- Candidate-initiated interview-stage changes remain unimplemented. The ratified direction is a new linked `role_profile_id` with blank evidence; it must not mutate the existing path or port practice history.
- Prep-context resolution and setup-session insertion are currently two durable statements rather than one transaction. A failed session insert can leave a candidate-owned profile with no practice activity; retry safely reuses it, and future selectors must not imply evidence from profile existence. Make the combined write transactional before production setup launch if empty profiles become user-visible or operational cleanup becomes necessary.
- Setup-session creation still lacks a request-level idempotency key. The UI suppresses ordinary duplicate submit, and prep-profile creation is concurrency-safe, but two accepted setup requests can create two sessions. Add setup-start idempotency before production network-retry and multi-tab acceptance testing.
- Dashboard Coach Update/detail presentation remains scaffold UI, but its read path now requires a matching completed versioned artifact and excludes unanswered plan items. Production synthesis/provider wiring, final interaction design, durable queue/builder surfaces, coach bundles, trend views, and multi-round aggregation remain unbuilt.
- Coach Update claim recovery currently uses a two-minute lease suited to the synchronous local fixture. Production synthesis must ratify that lease against provider/runtime budgets or add a heartbeat before asynchronous or long-running generation is enabled.
- Candidate-visible attempt counts are deliberately deferred. Keep attempt lineage and rollups available in data/read models, but do not spend current UI scope on count chips, labels, or charts before the core session and dashboard surfaces are productized.
- `feedback_actions_json` preserves only the latest recovery action per question. Decide before analytics/BI work whether full feedback-stage engagement needs an append-only event boundary; immutable answer attempts already preserve actual retry behavior.
- Sensitive data can still be too visible in AI-quality/debug surfaces until masking/redaction work lands.
- Historical candidate implementation tests are not fully restored on the cleanroom branch; keep `npm run test:candidate` scoped to deliberately restored surfaces.
