### Near-Term Architecture

- Production question wording passed synthetic, disposable-DB, guarded browser reconciliation, and request-idempotent setup replay; broader role/stage quality review and deployment approval remain open.
- Expand evaluator golden assertions to challenge marker-to-criterion consistency. The current thin-answer live case produced useful candidate coaching but internal `clear` bands that look too generous for its missing direct answer and detail markers.
- Resume upload/OCR, storage, revision labels, and question reconciliation are unratified. Interview-stage changes should create linked blank-slate prep contexts rather than mutating evidence history.
- Direct fixed-intent creation and intent-consume/session-create are separate, landed idempotency boundaries. Editable next-round queue launch remains distinct and uses its own draft/version contract.
- Pending Coach Update does not poll. Explicit repair exists for unavailable completed work, but background/long-running generation needs a lease, refresh, and retry contract.
- Full-history dashboard reads are correct but may require a versioned projection after volume measurements justify it.
- Production TTS, voice, and photo capture remain separate privacy and authorization projects. Invited live-practice convergence, the recruiter operational dashboard, and the employer-safe question/latest-answer transcript are landed. Candidate coaching remains private; broader employer content would require a new explicit contract and matching candidate disclosure.
- Standalone recruiter V2 uses app-owned Postgres authentication plus app-owned bulk email, with TalentArbor copy handoff as a complementary fallback. Candidate host launch does not automatically authenticate recruiters; later TA recruiter launch requires its own external identity, entitlement, candidate/job authorization, route, and cookie contract.
- Recruiter delivery is data-safe under replay and partial failure, but credentialed SMTP acceptance, 100-recipient deployed-duration measurement, bounce/event availability, and an operations policy for `outcome_unknown` remain required. If synchronous fan-out exceeds the function budget, move the same attempt ledger behind a durable worker/outbox rather than weakening replay fences.
- The public `Employee login` affordance resolves to the app-owned recruiter login. Registration, password recovery, MFA, administrator unlock/support, and future TA recruiter launch remain separate identity-policy work.
- Invitation token persistence uses SHA-256 lookup hashes plus AES-256-GCM ciphertext derived from `ENCRYPTION_SECRET`; plaintext is not stored. Before production key rotation, add an explicit bounded key ring/read window so changing the secret does not strand live invitation links. Final token lifetime remains a product/security decision.
- The owner-fenced invitation detail is the only recruiter read allowed to decrypt an active token into a copyable link. Dashboard/list/API responses remain bearer-free; expired, revoked, key-unavailable, accepted, in-progress, and unknown-outcome states never acquire a delivery action merely because the handoff is reopenable.
- `/s/[token]` removes bearer material from the browser URL immediately, but production edge, proxy, and upstream access-log redaction for that exchange path remains a release gate. The invitation bearer is intentionally reusable until expiry or revocation because it is the invited candidate's return mechanism.
- One invite-session cookie represents one current invitation in a browser profile. Opening a different invitation replaces that clean-route context; either original invitation link can establish its own context again. Completed entry now recovers to a minimal acknowledgement; token regeneration/revocation controls and a productized abandoned-entry presentation remain deferred.
- Exploratory dashboard/settings/reference/resume documents and demo routes contain useful visual ideas alongside unratified product claims. Treat them as design inputs only. Any preparedness percentage, `Strong`/`Emerging` rollup, recruiter-sharing control, evaluator-strictness setting, resume replacement flow, or reference-library benchmark must earn a separate product, privacy, and data-contract decision before runtime use.
- New interactive mockups belong in an isolated `.untracked/ui-lab` Vite app, not `src/app`; static studies may live under the excluded design-doc tree. Mockup promotion requires a spec decision and production implementation against real contracts. See [Design system foundation](./03-design/design-system-foundation.md#live-mockup-isolation).

- A nonproduction browser bridge remains where durable identity/storage is unavailable.
- Candidate-visible attempt counts and trends are deliberately deferred; lineage and rollups must remain intact.
- `feedback_actions_json` stores latest recovery state, not full append-only engagement history. Decide before BI work whether a separate event boundary is required.
- Expired setup-start claim rows are indexed but do not yet have a scheduled retention job; add bounded cleanup before production volume makes it operationally relevant.
- Expired direct-intent creation request rows are indexed but do not yet have a scheduled retention job; add bounded cleanup before production volume makes it operationally relevant.
- Expired or abandoned recruiter question-set claims are indexed but do not yet have a scheduled cleanup job. Authenticated fresh action keys are not rate-limited yet; both controls are required before a recruiter pilot.
